# Integrate, upgrade or remove 0-CODE 2.1.0

You are the owner's agent in an existing project, using Claude Code, Codex or OpenCode. Complete the requested lifecycle action in one session. Preserve project code, documents, tools, settings and login.

Development acceptance for 2.1.0 used Windows and Node 24; it did not cover Linux, macOS or Node 20/22. A configured CI matrix is not evidence of execution. Read the [validation scope](docs/PROJECT_SETTINGS.md#validation-scope), including filesystem and coverage limits, before reporting compatibility.

1. Identify the project root and the requested action. Obtain the public source from `https://github.com/0-SOFT/0-CODE`, optionally at a chosen release tag, or use the owner's reviewed local checkout. Clone into a temporary directory outside the project. Reading this public repository needs no token. Never put a token in a URL, print it, or copy engine authentication.
2. Run `node <source>/tools/0code.mjs scan --project <project> --json`. Summarize documents, engines, tools, MCP, check commands, old installation and collisions. New installations default all nine document roles to `.0-code/docs/`; explicit external roles retain priority. Keep product documentation separate. Ask one list of genuinely ambiguous choices: document roles, engines, modules, toolset scope and collisions. Use suggested defaults otherwise. Never resolve a collision by deleting or overwriting owner files.
3. Create a separate project branch. Save the reviewed `suggestedConfig` with chosen changes to a temporary JSON file; the scan envelope itself is not a configuration. [PROJECT_SETTINGS](docs/PROJECT_SETTINGS.md) is the reference. Explicitly ask where to install the toolset: `user` shares one selection across the machine; `project` keeps the source selection in this project. Explain the preview's native engine changes before applying: user delivery can write tools and MCP settings in `~/.claude`, `~/.codex` and OpenCode's user config; project delivery uses project engine directories. Removing the framework preserves machine tools; `uninstall-tools` restores their owned native settings separately. Inspect selected MCP prerequisites first: the manifest version is a tested SemVer minimum, not a required downgrade. Preserve a newer installed package with the correct name and entry; install only absent or older prerequisites in the agreed scope, and provide optional credentials through the environment.
4. Preview, inspect and apply through the same CLI:
   - New project: `install --project <project> --config <config> --dry-run`, then omit `--dry-run`; selected user tools install automatically.
   - Upgrade: `upgrade --project <project> --source <source> --dry-run`, then apply; preserve preferences and documents.
   - Move standard 2.0.x `docs/*` cycle roles inside: ordinary upgrade keeps paths. Finish the cycle, collect jobs and stop the driver; prepare an exact reviewed file list, then `upgrade --project <project> --relocate-documents <files.json> --dry-run` from the new source and apply. `migrate` also accepts this flag. Existing STATE/ROADMAP and templates requiring pointer updates must be listed. Unlisted product documents remain; custom external roles are not relocated. Review config, STATE pointers, template changes and archived original bytes; stage moves together for Git rename detection.
   - Customized `.0-code/` without a receipt: review every code file and exact project extension, save SHA-256 hashes with `replace`/`preserve` actions, then `migrate --project <project> --config <reviewed-config.json> --adopt-manifest <manifest.json> --dry-run` from the new source and apply. Adoption replaces and archives code, preserves reviewed `bin/`, `claude/` and README extensions, and keeps existing roles. Save custom AGENT rules as a durable document referenced in `instructions.project_rules`. Stop/guard collisions, changed hashes, unknown files, active cycles and live locks refuse. Relocation is a separate operation. See [manifest formats and examples](docs/PROJECT_SETTINGS.md).
   - Old root-based 1.x: the public source excludes `config/legacy-installations.json`, so it cannot build an automatic migration plan. Use `migrate --project <project> --source <evidence-source> --dry-run`, then apply, only when that source contains the published ownership evidence. Stop any live old cycle first. Without evidence, preserve old files and review ownership; do not delete files merely because their names resemble the framework.
   - Remove: `node <project>/.0-code/tools/0code.mjs uninstall --project <project> --dry-run`, then apply. Cycle documents, their directories and adopted extensions remain; original session settings are restored. Runtime and archives are removed, so save needed backups first. Remaining extensions require explicit adoption before reinstall. Machine tools remain until separately requested `uninstall-tools`; that command restores their original native settings.
5. After install, upgrade or migration run `node <project>/.0-code/tools/0code.mjs doctor --project <project> --json` and the project's real checks. Repair your errors and report concrete remaining conflicts or unsupported formats. Do not declare completion while doctor fails. After removal verify owner file preservation. Explain the result and commit the completed project change in its branch; push when the owner requested it.
6. When committing an install or upgrade, use `git add --renormalize .0-code` before staging the completed changes. The namespace's own `.gitattributes` preserves receipt hashes across clones without changing the project's text policy. Never stage ignored runtime backups.
7. Explain the first cycle: fill the single `.0-code/templates/cycle.md`, save it under the configured prompts role (new default `.0-code/docs/prompts/`), then `node .0-code/tools/0code.mjs start <prompt> [--max N]`. Start prints the driver command. Restart Claude for new hooks; Codex and OpenCode use the supervisor. One folder runs one cycle. Authentication stays with the engine. Unspecified model and effort inherit owner preferences; explicit flags, environment and project configuration take precedence in that order. See [ENGINE_SETTINGS](docs/ENGINE_SETTINGS.md).

For Claude without editing `CLAUDE.md`, select `instructions.claude: session-hook`. Hooks load `.0-code/AGENT.md` at SessionStart and SubagentStart. The default `.claude/settings.json` applies to normal project sessions; `instructions.claude_settings: .0-code/claude/settings.json` isolates a session overlay and requires `claude --settings .0-code/claude/settings.json` or a launcher passing it. Keep reviewed launcher, MCP, system-prompt and settings policies. Ordinary Claude sessions do not load the overlay automatically. A previous owned `CLAUDE.md` block requires uninstall under `project-file` mode before reinstall with saved config. Doctor checks native wrappers and project/local hook disabling; user, managed and CLI overrides remain outside that check. Other selected engines retain their necessary native instructions, hooks, guard plugin and tool registrations.

The public [tool catalog](toolset/CATALOG.md) selects only `context7`, `playwright`, `chrome-devtools`, `sequential-thinking` and `memory`. Private skill, agent, command and rule bodies are excluded; do not promise to install them from this checkout. These five MCP need local npm prerequisites, not external API keys; browser tools also need a browser. Optional account examples in the manifest require explicit configuration and authorization. A successful doctor checks local prerequisites and ownership, not a live MCP connection.
