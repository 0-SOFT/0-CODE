# Integrate, upgrade or remove 0-CODE 2.1.1

You are the owner's agent in an existing project, using Claude Code, Codex or OpenCode. Complete the requested lifecycle action in one session. Preserve project code, documents, tools, settings and login.

Read the measured platforms, Node versions and filesystem/coverage limits in the [validation scope](docs/PROJECT_SETTINGS.md#validation-scope) before reporting compatibility. A configured CI matrix is not evidence of execution.

1. Identify the project root and the requested action. Obtain the public source from `https://github.com/0-SOFT/0-CODE`, optionally at a chosen release tag, or use the owner's reviewed local checkout. Clone into a temporary directory outside the project. Reading this public repository needs no token. Never put a token in a URL, print it, or copy engine authentication.
2. Run `node <source>/tools/0code.mjs scan --project <project> --json`. Summarize documents, engines, tools, MCP, check commands, old installation and collisions. New installations default all nine document roles to `.0-code/docs/`; explicit external roles retain priority. Keep product documentation separate. Ask one list of genuinely ambiguous choices: document roles, engines, modules, toolset scope and collisions. Use suggested defaults otherwise. Never resolve a collision by deleting or overwriting owner files.
3. Create a separate project branch. Save the reviewed `suggestedConfig` with chosen changes to a temporary JSON file; the scan envelope itself is not a configuration. [PROJECT_SETTINGS](docs/PROJECT_SETTINGS.md) is the reference. Explicitly ask where to install the toolset: `user` shares one selection across the machine; `project` keeps the source selection in this project. Explain the preview's native engine changes before applying: ordinary user delivery can write tools and MCP settings in `~/.claude`, `~/.codex` and OpenCode's user config; ordinary project delivery uses project engine directories. Isolated Claude install/upgrade/migrate never runs machine tool installation automatically, even with user scope; use a separate, explicitly requested `install-tools` action. Project scope alone does not authorize external Claude files in that mode. Removing the framework preserves machine tools; `uninstall-tools` restores their owned native settings separately. Inspect selected MCP prerequisites first: the manifest version is a tested SemVer minimum, not a required downgrade. Preserve a newer installed package with the correct name and entry; install only absent or older prerequisites in the agreed scope, and provide optional credentials through the environment.
4. Preview, inspect and apply through the same CLI:
   - New project: `install --project <project> --config <config> --dry-run`, then omit `--dry-run`; ordinary integration installs selected user tools automatically. Isolated Claude requires the separate explicit action described above.
   - Upgrade: `upgrade --project <project> --source <source> --dry-run`, then apply; preserve preferences and documents.
   - Move standard 2.0.x `docs/*` cycle roles inside: ordinary upgrade keeps paths. Finish the cycle, collect jobs and stop the driver; save the complete pre-operation config outside `.0-code/` as `<saved-before.json>` and prepare an exact reviewed file list. Run `upgrade --project <project> --relocate-documents <files.json> --dry-run` from the new source and apply. `migrate` also accepts this flag. Existing STATE/ROADMAP and templates requiring pointer updates must be listed. Unlisted product documents remain; custom external roles are not relocated. Review config, STATE pointers, template changes and archived original bytes; stage moves together for Git rename detection. If an interrupted relocation refuses recovery after publishing its new config, keep the cycle stopped, review the saved config and original manifest, then rerun the original applying command with both `--config <saved-before.json>` and the original `--relocate-documents <files.json>`, without `--dry-run`. Dry-run does not recover pending transactions and may refuse until recovery finishes. A transaction journal's previous config alone grants no external recovery authority.
   - Customized `.0-code/` without a receipt: review every code file and exact project extension, save SHA-256 hashes with `replace`/`preserve` actions, then `migrate --project <project> --config <reviewed-config.json> --adopt-manifest <manifest.json> --dry-run` from the new source and apply. Adoption replaces and archives code, preserves reviewed `bin/`, `claude/` and README extensions, and keeps existing roles. Save custom AGENT rules as a durable document referenced in `instructions.project_rules`. Stop/guard collisions, changed hashes, unknown files, active cycles and live locks refuse. Relocation is a separate operation. See [manifest formats and examples](docs/PROJECT_SETTINGS.md).
   - Old root-based 1.x: the public source excludes `config/legacy-installations.json`, so it cannot build an automatic migration plan. Use `migrate --project <project> --source <evidence-source> --dry-run`, then apply, only when that source contains the published ownership evidence. Stop any live old cycle first. Without evidence, preserve old files and review ownership; do not delete files merely because their names resemble the framework.
   - Remove: `node <project>/.0-code/tools/0code.mjs uninstall --project <project> --dry-run`, then apply. Cycle documents, their directories and adopted extensions remain; original session settings are restored. Runtime and archives are removed, so save needed backups first. Remaining extensions require explicit adoption before reinstall. Machine tools remain until separately requested `uninstall-tools`; that command restores their original native settings.
5. After install, upgrade or migration run `node <project>/.0-code/tools/0code.mjs doctor --project <project> --json` and the project's real checks. Repair your errors and report concrete remaining conflicts or unsupported formats. Do not declare completion while doctor fails. After removal verify owner file preservation. Explain the result and commit the completed project change in its branch; push when the owner requested it.
6. When committing an install or upgrade, use `git add --renormalize .0-code` before staging the completed changes. The namespace's own `.gitattributes` preserves receipt hashes across clones without changing the project's text policy. Never stage ignored runtime backups.
7. Explain the first cycle: fill the single `.0-code/templates/cycle.md`, save it under the configured prompts role (new default `.0-code/docs/prompts/`), then `node .0-code/tools/0code.mjs start <prompt> [--max N]`. Start prints the driver command. Restart Claude for new hooks; Codex and OpenCode use the supervisor. One folder runs one cycle. Authentication stays with the engine. Unspecified model and effort inherit owner preferences; explicit flags, environment and project configuration take precedence in that order. See [ENGINE_SETTINGS](docs/ENGINE_SETTINGS.md).

For isolated Claude, select both `instructions.claude: session-hook` and `instructions.claude_settings: .0-code/claude/settings.json`, then launch with `claude --settings .0-code/claude/settings.json` or a reviewed launcher passing it. With only Claude and internal documents, install, upgrade, migrate and adoption must have zero unselected external writes, deletions or recovery changes. Inspect the complete plan, including cleanup and recovery: `.claude/`, `.mcp.json`, `CLAUDE.md` and machine profiles are outside that session's integration. Only explicit external document roles, other selected engines and separately requested machine actions authorize their corresponding external changes. Old receipts and unfinished journals do not authorize external cleanup. If a transition requires it, save config and documents, review uninstall/cleanup under the previous mode, then reinstall in isolated mode; do not silently drop the conflicting operations or edit owner files.

SessionStart and SubagentStart load `.0-code/AGENT.md`, whose catalog points to internal orchestrator and enabled audit sources. Read the exact procedure source when requested by the user or active cycle prompt; native slash commands are not registered. `modules.audits: false` removes audit sources and references. Safe text tools can use internal references; native execution controls and new MCP registrations that cannot be preserved are `unsupported` and require a separate integration decision. Keep reviewed launcher, MCP, system-prompt and settings policies. Compatible overlay settings gain framework entries, and uninstall restores their original values. Ordinary Claude sessions do not load the overlay automatically, though existing owner and user tools remain discoverable. Doctor checks native wrappers and project/local hook disabling; user, managed and CLI overrides remain outside that check. Ordinary `project-file` mode and `session-hook` with default `.claude/settings.json` retain their native tools and hooks; other selected engines retain their necessary integration.

The public [tool catalog](toolset/CATALOG.md) selects only `context7`, `playwright`, `chrome-devtools`, `sequential-thinking` and `memory`. Private skill, agent, command and rule bodies are excluded; do not promise to install them from this checkout. These five MCP need local npm prerequisites, not external API keys; browser tools also need a browser. Optional account examples in the manifest require explicit configuration and authorization. A successful doctor checks local prerequisites and ownership, not a live MCP connection.
