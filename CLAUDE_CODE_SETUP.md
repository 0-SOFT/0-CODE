# Claude Code setup

Use the public source at `https://github.com/0-SOFT/0-CODE`. Follow [INTEGRATE](INTEGRATE.md) for the agent workflow or [QUICKSTART](QUICKSTART.md) for manual installation. Select `claude`; Codex and OpenCode use the same lifecycle CLI with their own adapters. All project options are defined once in [PROJECT_SETTINGS](docs/PROJECT_SETTINGS.md).

For Claude, the default installer merges required hooks into `.claude/settings.json` and a short owned reference into `CLAUDE.md`. `AGENTS.md` is used only when Codex or OpenCode is selected. Commands point into `.0-code/`; existing owner settings and instructions are preserved. Foreign Stop and PreToolUse control hooks are explicit collisions. There is no Claude plugin installation mode.

In 2.1.1, `instructions.claude: session-hook` loads `.0-code/AGENT.md` through SessionStart/SubagentStart without writing `CLAUDE.md`. Default `.claude/settings.json` keeps normal project integration. Add `instructions.claude_settings: .0-code/claude/settings.json` for strict session isolation, then launch `claude --settings .0-code/claude/settings.json`, use the framework supervisor or a reviewed launcher passing that file. Install/upgrade/migrate/adoption make no unselected external writes, deletions or recovery changes; explicit external document roles, other selected engines and separately requested machine actions are scoped exceptions. Old receipts and journals do not authorize external cleanup. Switching from owned external Claude entries requires reviewed cleanup under the previous mode; an owned `CLAUDE.md` block specifically requires uninstall under `project-file` before reinstall with saved config.

Both context hooks expose internal orchestrator and enabled audit procedure sources through AGENT references; native slash commands are not registered. With `modules.audits: false`, audit sources and references are absent. Safe text tools can be referenced, while incompatible native execution controls and new MCP registrations receive `unsupported`. Keep reviewed launcher, MCP, system-prompt and settings policies. Compatible settings gain framework entries; uninstall restores original values. Ordinary sessions do not load the internal overlay automatically, and existing project settings remain unchanged. Hooks must remain enabled. Doctor checks local wrapper output and project/local disabling, not user, managed or CLI overrides. See [PROJECT_SETTINGS](docs/PROJECT_SETTINGS.md).

Restart the Claude session after installation or hook changes: settings load at session startup. Run `node .0-code/tools/0code.mjs doctor --json`, fill `.0-code/templates/cycle.md`, save it under the configured prompts role (new default `.0-code/docs/prompts/`), then use `start`. In the project session, follow the active state task. The Stop hook continues turns and checks genuine blockers, release completion and enabled limits. An external supervisor is an alternative driver; never start both for one folder.

Native login and personal MCP stay with Claude. Unspecified model and effort inherit owner preferences; precedence is explicit flags, environment, project configuration, then native settings. Authentication is never copied. The public catalog includes only five default MCP: context7, playwright, chrome-devtools, sequential-thinking and memory. Private tool bodies are excluded. Valid newer npm prerequisites are preserved; these five need no external API key, while browser tools need a browser. Ordinary user tool delivery uses native user locations; choose the scope explicitly before installation. Strict session lifecycle actions require a separately requested `install-tools` for machine tools, even with user scope. Stock tools do not add global cycle hooks or permissions. Project scope pins a project selection while respecting the session boundary. [ENGINE_SETTINGS](docs/ENGINE_SETTINGS.md) documents environment overrides, guard modes, headless permissions and native `ask` rules.

Session logs and usage status line are optional modules. Claude hooks capture native transcripts and summaries; the supervisor records attempt journals for all three engines under the configured logs role when `session_logs` is enabled, including failures and retries. Journals do not duplicate usage accounting. An incompatible existing status line requires an integration decision. Bot notifications require explicit Telegram credentials; without them notifications do not occur. Logs can contain owner data and belong in the ignored logs role, default `.0-code/docs/logs/`, optionally `.0-code/run/logs/`.

Upgrade an existing `.0-code/` installation through the lifecycle CLI; configured paths stay in place. Explicit `--relocate-documents` moves reviewed standard external cycle files after completion. Customized installations without a receipt use a reviewed `--adopt-manifest`; launcher, MCP, system-prompt and compatible session policies remain. Documents and retained extensions survive uninstall, original session settings are restored, and runtime archives are removed. See the complete examples in [PROJECT_SETTINGS](docs/PROJECT_SETTINGS.md).

The public source excludes `config/legacy-installations.json`; automatic migration of a root-based 1.x installation requires a separate source with published ownership evidence. Stop the old cycle, preview that historical migration and retain backups; without evidence, preserve old root files and review their ownership.
